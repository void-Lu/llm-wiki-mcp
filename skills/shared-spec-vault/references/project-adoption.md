# 项目采用与适配

在公共规范回写项目、核对项目是否需要跟随公共规范调整时读取。

## 适用性

核对项目语言、平台、框架、版本、实际运行环境及架构前提。每个非空 `applies_to` 维度内的值为可选项，与项目至少匹配一项；非空维度之间同时满足，空维度不限制。解释 `conditions` 的匹配依据，尤其是公司策略、个人偏好及项目是否采用该策略。示例语言和来源项目名称不能代替适用性判断。

用 `wiki_list` 完整枚举 `wiki/entities/shared-specs/`，再按各页 `content_ref` 调 `wiki_get(include_body=true)` 读取正文和 frontmatter。模糊检索仅辅助导航，不能代替完整枚举。

## 选择写入方式

- **原文导入**：用户要求直接采用公共页原文时，保留正文，在明确目标写入；知识库专属 frontmatter 不随正文带入项目。
- **项目适配**：用户要求检查、更新、整合项目规范时，把适用规则融入现有章节；保留仍有效的本地规则、项目策略和案例。逐条核对触发条件、适用范围、例外及证据强度，避免把案例推广为通则，或把公司、个人偏好提升为平台要求。

一次适配可以涉及多个公共页和项目文件。以规则语义为单位建立对应关系，不假定一个公共页必须生成一个项目文件。只有发现确实需要调整的内容才提出修改。

## 目标与审核

1. 先读取项目现有 spec 索引和相关规则。`derived_from` 是来源线索；只有对应当前项目且结构仍适用时才用它推导目标，其他项目的来源路径不直接决定本项目位置。
2. 能从现有结构判断时，提出目标文件或章节；仅在目录归属或规则含义存在实质歧义时向用户确认。
3. 逐条分类：新建、重复/unchanged、冲突、相关可合并；展示依据和最终文件 diff。冲突需要给出具体处置方案，不能用公共页全文替换来隐含决定。
4. 将适用且获授权的规则逐条落实到目标，必要时去重并更新项目现有索引。额外发现的规则调整另列，不能夹带写入。

## 写入与验收

写入前重新核对公共页和项目目标版本；漂移时按主文件的授权规则重新预览。单文件使用临时文件原子替换，多文件按完成预览核对且处于授权范围的变更集合执行，并记录当前任务的完成进度。

回读每个修改后的文件，核对采用规则的条件、动作、例外及保留的项目差异；检查索引指向最终位置。重组涉及拆合、移动或删除时按[文档迁移](document-migration.md)执行。用户要求同步知识库时，先完成本地最终状态，再进入主文件的 `sync` 阶段。
